## 方式一
1. 使用fork()创建子进程
	1. 父进程调用exit退出；
	2. 子进程继续执行；
2. 子进程调用setsid函数
	1. `setsid()` 在 Unix/Linux 下只有一件事：**创建一个新的会话（session）并让调用进程成为该会话的“会话领头进程”(session leader)**，同时该进程也成为新进程组的组长。这一动作附带三个效果：
		1. **脱离原控制终端**——即使终端关闭，进程也不会收到 SIGHUP；
	    2. **与原进程组隔离**——不再继承父进程的进程组 ID；
	    3. **获得新的会话 ID**——等于调用进程的 PID。因此它是把普通进程变成守护进程（daemon）最关键的一步
### 针对MacOS的特殊设置
// In Mac OS X, fork()'d child processes can't use most APIs (the frameworks
// that Deskflow uses in fact prevent it and make the process just up and die),
// so need to exec a copy of the program that doesn't fork so isn't limited.
```cpp
int execSelfNonDaemonized()
{
	extern char **NXArgv;
	char **selfArgv = NXArgv;
	setenv("_DESKFLOW_DAEMONIZED", "", 1);
	execvp(selfArgv[0], selfArgv);
	return 0;
}
```
>1. **macOS 的框架限制**  
    macOS 的高层框架（如 CoreFoundation、AppKit、Security、Quartz 等）在内部使用了 Mach 端口、线程池、RunLoop 等资源，这些资源在 `fork()` 后的子进程中**不再有效**。调用任何相关 API 会触发 **`__THE_PROCESS_HAS_FORKED__` 断言**，导致进程**强制退出**（crash）。
>2. **exec 的作用**  
    `exec` 会**完全替换当前进程映像**，重新初始化运行时环境，重新加载框架。这样新进程就不再是“fork 出来的”，而是“重新启动的”，从而**绕过了 macOS 对 fork 后使用框架的限制**。
>3. **Deskflow 的应对策略**  
    Deskflow 需要在后台运行辅助进程（如屏幕共享、权限代理等），但又不能直接在 fork 后的子进程中继续工作。因此采用 **“fork + exec 自身”** 的经典模式：
>- 父进程 fork 出子进程；
>- 子进程立即 `exec` 同一个二进制文件，但带上特殊参数（如 `--child-mode`），让它以“非 fork”身份重新启动；
>- 新进程即可正常使用 macOS 框架，而不会触发崩溃。
